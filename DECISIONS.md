### Follow-up: stock experimental-part route

The earlier custom-preflight blocker has a plausible public-API solution. A reward-gated Lodeworks `PART` uses `techRequired = lodeworksBlueprintLocked`, an ID deliberately absent from the stock tech tree. In the installed assembly, `ResearchAndDevelopment.PartTechAvailable` and `PartModelPurchased` consult `experimentalPartsStock` when `TechRequired` has no researched node. `AddExperimentalPart(AvailablePart)` and `RemoveExperimentalPart(AvailablePart)` are public; `OnSave` writes `ExpParts`, and `OnLoad` clears and reloads it from the current save. `EditorLogic.GetStockPreFlightCheck` and `LaunchSiteFacility.launchChecks` both add `PreFlightTests.ExperimentalPartsAvailable`; its `Test` consults `IsExperimentalPart`, and `GetProceedOption` returns null. Thus the stock preflight appears to prevent an unrewarded imported craft from launching without a custom hook. These are verified assembly control-flow observations, not an in-game result.

`Phase1BlueprintAdapter` now checks that the sentinel tech node is absent, verifies every controlled part is configured to use it, checks its separate stock science prerequisite, reconciles only scenario-supplied reward entitlements through the stock experimental-part API, and refreshes the editor when availability changes. It does not mutate part prefabs. The adapter is not yet called by a persisted campaign scenario; that integration and the clean-game checks remain. The research prerequisite is kept separately because an absent `techRequired` node cannot itself represent both the stock tech and the campaign reward. If a tech-tree mod creates the sentinel node, reconciliation fails closed instead of allowing an ordinary R&D purchase.

`tools/Verify-Phase1BlueprintApi.ps1 -KspRoot $env:KSP_ROOT` repeats the relevant metadata/control-flow assertions on a local installation. The reference API documentation also lists the [experimental-part methods](https://kspmoddinglibs.github.io/KSPDocsSite/class_research_and_development.html); the installed assembly is the version-specific authority for this result.

### Runtime finding from the Phase 1 harness — 2026-10-03

The first interactive sandbox run loaded the diagnostic PART and allowed it to launch, but `KSP.log` showed `Lodeworks.Sim` failing type load because KSP_x64 could not resolve `netstandard, Version=2.0.0.0`. This invalidates the earlier assumption that a successful `netstandard2.0` build and a two-DLL package prove runtime loadability. Multi-target `Lodeworks.Sim` for `netstandard2.0` and `net48`; KSP now references and stages only the `net48` build. This keeps the pure library independent of KSP while avoiding a runtime facade dependency. Do not package a .NET or game DLL as a workaround. The package verifier checks references and contents, but a fresh game load is still required.

The same run showed `ResearchAndDevelopment.Instance` is absent in sandbox. Sandbox already makes the probe part available through stock rules; the diagnostic harness now verifies the configured PART without calling the career R&D adapter in that mode. Career/science reconciliation still uses the actual adapter. The sandbox observation alone cannot prove career locks or imported-craft preflight.

In the corrected modded KSP 1.12.5 run, the tester observed a locked career probe, reward gated by `basicScience`, persistence across reload, existing-vessel loading after revoke, and save isolation. The imported craft's generic stock preflight warning became actionable evidence only after the *same craft* launched when the reward was granted without another change. This supports the stock route in that installation; a clean-install run remains before treating the part-lock gate as accepted.

A subsequent `SCIENCE_SANDBOX` run showed the same reward-plus-stock-science gating in the tester's modded installation. The diagnostic log recorded all four availability flags false before researching `basicScience` and all four true afterward. A clean Squad-plus-Lodeworks run remains the validation gate for this part-lock route.

### Docking and fuel follow-up — 2026-10-03

## Phase 2 — 2026-10-04

- Treat `AI Master command prompt` revision 5 sections 3.4, 4.1-4.3, 6, 17, and 18 as the Phase 2 authority. `tools/Phase2-Scope.md` defines the boundary. Preserve accepted Phase 1 and stop before Phase 2A's ReservationBook, floors, and escrow.
- Before implementing behavior, inspect the local Steam KSP 1.12.5 / build 03190 `Assembly-CSharp.dll` with installed Mono.Cecil. Confirm public `PartResourceLibrary.Instance/GetDefinition(string)`, `PartResourceDefinition.density/unitCost` (single), `Funding.Instance/Funds/CanAfford(float)/AddFunds(double, TransactionReasons)`, and `ConfigNode` value APIs. Save the repeatable ten-assertion verifier as `tools/Verify-Phase2KspApi.ps1`. Installed Squad `ResourcesGeneric.cfg` lists LF/OX density `0.005` and unit costs `0.8`/`0.18`. The new adapter reads and validates runtime metadata only; no fuel or funds are written.
- Represent all non-stock goods in a pure ledger with explicit resource kinds and density, and take LF/OX density and unit cost as immutable validated KSP inputs. An ore lot retains batch ID, origin body/biome, grade, units, provenance class, campaign eligibility, and creation sequence. Only matching origin, exact poor/normal/rich grade band, provenance, and eligibility may stack; weighted average stays in-band. Inventory keeps different batch IDs separate even when stack-compatible so later acceptance-time sublots retain their identity. Debug/tutorial ore is ineligible for campaign credit but can be processed. Phase 2A will exclude committed lots from selection.
- Give each inventory only its configured integrated capacity plus dedicated units of the **same** resource. A storage unit never grants contents. A removal that would strand contents is rejected. Starter receipts contain exactly nine persistent tokens per hab; repeated grant/reload cannot issue a second set. The integrated terminal consumes its terminal token. Packing preserves condition/tier; the Phase 2 API cannot upgrade or repair a token for free. Paid upgrades and deployment wiring belong to Phase 10.
- Aggregate repeated recipe legs before checking limits. Input shortages, full non-dump outputs, and quoted power can cap active time; only final binding reasons are returned. Slag dump records the discarded amount and avoids a slag-storage stall. Smelting conserves ore/metal/slag under origin yield <=1. Machine and Pack are intentionally not mass-conserving chemistry. Zero crew/rate yields no work. Pure quote inputs do not mutate caller pools.
- Use `MaterialCommandBook` as Phase 2's atomic authority for immediate bulk/ore transfers, material consumption, and single-inventory recipe material commits. Stage copies and publish them only on success; save command receipts in versioned pure snapshots so duplicate IDs cannot replay after restore. The `Process` power budget is a quote input, **not** a live power debit; no gameplay caller may invoke it until Phase 6 can atomically commit owned power. Inventory direct mutators are construction/test helpers and have no game caller; Phase 2A must migrate every future claimant to ReservationBook rather than adding a second reservation dictionary.
- Automated result with `KSP_ROOT` pointing to the local Steam installation: both Release builds succeeded with zero warnings/errors; 18/18 tests passed (13 new Phase 2 fixtures plus 5 predecessor tests); Phase 1 blueprint verifier passed 11 checks; runtime package remained exactly two normal DLLs and separate opt-in harness. No Phase 2 in-game test was claimed. The modded Steam install was not altered. Pure snapshot round-trips are verified, while live scenario persistence starts in Phase 4 and all section 19.2 gameplay gates remain open.

## Phase 2A — 2026-10-04

- Start after Phase 2 PR #7 merged. Follow master revision 5 sections 4.3-4.4 and 18.1-18.2 and the explicit `tools/Phase2A-Scope.md` checklist. This phase is pure reservation authority; Phase 3A chronological allocation and live gameplay remain outside its scope.
- Keep a single `ReservationBook` of individually identified claims. Compute stock, incoming-capacity and slot availability from physical inventory/supply minus active claims, rather than a second reserved-total ledger. Matter reservations name an exact ore batch when the resource is ore. Protected floors apply to overlapping lots; quota floors are bounded by the remaining objective after assigned cargo. Only explicit campaign-export or manual-override claims may name floor IDs to bypass.
- Move claimed stock into escrow exactly once on commit. Escrow is physical matter owned by its claim and contributes mass, but is absent from available inventory. Partial return and consumption update the same record and use receipts. A return must also respect newer incoming-capacity promises. Remove-storage commands must preserve incoming-capacity claims. Keep direct inventory mutators as construction helpers; the `MaterialCommandBook` is the transaction entry point.
- On pure snapshot restore, preserve conflicting claims as quarantined records with conflict reasons instead of silently accepting them or creating matter. Version 2 material snapshots include the ReservationBook; version 1 Phase 2 snapshots still restore. This is not Phase 4's live ConfigNode schema or scene persistence.
- Validation with local Steam KSP 1.12.5.3190 / build 03190 as build reference: solution and separate opt-in harness Release builds passed with 0 warnings/errors; 30/30 automated tests passed, including 12 Phase 2A fixtures; ten Phase 2 KSP API assertions and eleven Phase 1 blueprint assertions passed; normal package still consists of only the two Lodeworks DLLs. No new KSP API is called by Phase 2A and no in-game reservation behavior has been observed. The modded Steam installation and saves were not changed. PR #8 merged before Phase 3; the section 19.2 manual release gate is open.

## Phase 3 — 2026-10-04

- Follow master revision 5 sections 4.3-4.4, 7.1-7.3, 12 and 18 after Phase 2A PR #8 merged. `tools/Phase3-Scope.md` defines the pure boundary. No additional KSP API is needed or guessed. The world scheduler is one UT authority; every converter at an endpoint draws from the same Phase 2 material book and owned power account, and physical interval deltas are staged atomically through the Phase 2A ReservationBook.
- Resolve empty/full stock and battery boundaries from aggregate rates, then process timestamped events in section 12 phase order and stable ID order. Live generation supports production at zero stored battery charge. Persist the actual cursor, requested target, pending events, completed-event signatures, converter state, power and dumped-output totals in a versioned pure snapshot. A 4 ms frame wrapper or deterministic boundary-count limit leaves unapplied time visible. A rollback returns RequiresRestore rather than retaining newer state.
- Reject material-flow cycles for now so an empty pair of converters cannot bootstrap goods from each other. The pure inputless source converter is only a fixture/hook for Phase 5 extraction. Exact ore lots and overlapping protected floors remain guarded; incoming-capacity promises constrain production. Optional outputs fill capacity first and record later overflow rather than silently discarding all output. A blocked arrival preserves its pending event and cursor; recovery/waiting queues and structured dependency reasons belong to Phase 3A.
- Automated fixtures support the Phase 3 pure gate: 46/46 tests including 16 new world fixtures passed; Release solution and separate Phase 1 harness builds had 0 warnings/errors; installed KSP API checks and two-DLL package verification passed. No in-game scheduler check is claimed: no live caller or scene/save adapter exists yet, and the modded Steam installation was not changed. Phase 4 owns live schema persistence; Phase 5 owns deposits/extraction, Phase 6 solar/owned-power adapters, and Phase 3A owns chronological competing requests. The section 19.2 manual gate remains open.
